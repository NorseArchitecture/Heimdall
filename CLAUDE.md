## What This Realm Is

Heimdall is **the gate** — `Norse.AuthN`: the authn story built on Himinbjörg's identity record, presented uniformly across Blazor Server, WASM, and MAUI, with the backing gRPC contracts. Three projects:

| Project | Carries | Rule |
|---|---|---|
| `AuthN.Services` | The wire tier: `IAuthenticationService` (Login/Register/EmailExists/Logout, plus TwoFactorSignIn/RecoveryCodeSignIn/ForgotPassword/ResetPassword/ConfirmEmail/ConfirmEmailChange/ResendEmailConfirmation), `IIdentityService` (disclosure), and `IAccountService` (self-service account: GetAccountStatus/SetPhoneNumber/ChangePassword/SetPassword/ChangeEmail/GetExternalLogins/RemoveExternalLogin/DeletePersonalData — `GetAccountStatus` and `GetExternalLogins` are `CancellationToken`-only), their `[DataContract]` records (the account ones: `AccountStatusResponse`, `SetPhoneNumberRequest` — `Phone` is a nullable `Result<PhoneNumber>?` stamp, null = clear — `ChangePasswordRequest`, `SetPasswordRequest`, `ChangeEmailRequest`, `ExternalLoginsResponse`/`ExternalLoginEntry`/`ExternalProviderEntry`, `RemoveExternalLoginRequest`, `DeletePersonalDataRequest`), `AuthNPolicies`/`IdentityPolicies` (names only) | Thin by law — no Razor, no FluentValidation, no mediator coupling, and no issuance result record (every `IAuthenticationService` operation returns Asgard's `NavigationResult`/`BoolResponse` under `Outcome<T>`; the disclosure responses `PersonalDataResponse`/`MaskedPersonalDataResponse` and the account-state responses `AccountStatusResponse`/`ExternalLoginsResponse` are the tier's only response records). A consumer building their own UI references this and nothing else |
| `AuthN.Components` | Headless pages, the FluentValidation validators (Login/Register/GetMaskedPersonalData, plus TwoFactorSignIn/RecoveryCodeSignIn/ForgotPassword/ResetPassword/ConfirmEmail/ConfirmEmailChange/ResendEmailConfirmation, plus the account six SetPhoneNumber/ChangePassword/SetPassword/ChangeEmail/RemoveExternalLogin/DeletePersonalData), `Shared/ManageStatus` (the Manage redirect's `status` keys and their text), and the session-transition seam (`ISessionTransition`/`ForceLoadSessionTransition`/`AddNorseSessionTransition()`) | Platform-free RCL (NORSE073); no visual framework. `OutcomeFormComponentBase` and the `ServerValidation/` machinery were hoisted to Asgard's `Abstractions.Components` on 2026-08-09 and arrive by reference — do not reintroduce local copies |
| `AuthN.Components.FluentUI` | The visual skin: `GateLayout`, Login, Register, `ModelValidationSummary`, recovery-code display, ForgotPassword, ResendEmailConfirmation, and routable shims over plain-parameter units — `LoginWith2fa`→`TwoFactorForm`, `LoginWithRecoveryCode`→`RecoveryCodeForm`, `ResetPassword`→`ResetPasswordForm`, `ConfirmEmail`→`ConfirmEmailPanel`, `ConfirmEmailChange`→`ConfirmEmailChangePanel` (the confirm panels are click-to-confirm: a token is consumed on a click, never on load) — the account-management tree (`ManageLayout` and `ManageNavMenu` at the project root, a `FluentNav`/`FluentNavItem` menu; under `Manage/`, the loader-over-form pages `Index`→`ProfileForm`, `Email`→`ChangeEmailForm`, `ChangePassword`/`SetPassword`→the shared `PasswordPanel` (`ChangePasswordForm` or `SetPasswordForm` by `HasPassword`, title and heading following the chosen form; neither route redirects to the other), `DeletePersonalData`→`DeletePersonalDataForm`, plus `ExternalLogins` and the moved `PersonalData`; `Manage/_Imports.razor` stamps the layout and the `Account` policy on all of them, locked by `ManagePolicyLockTests`) — plus `wwwroot/` JS interop | The drop-in pattern — a different design system lands as a sibling, not an edit |

**Dependency posture:** Heimdall rides on nothing above Asgard, but the relationship with Himinbjörg runs both ways — Himinbjörg's `Identity.Web.Server` NorseRefs `AuthN.Components.FluentUI` (to host pages), through which `AuthN.Services` flows transitively for the contracts it implements, floating on `Version="*"` — so contract changes here ship and publish before Himinbjörg's handlers can compile against them. Heimdall is not unambiguously "topmost" in the chain.

**Component placement is a rule, not an inventory — the tree is the truth.** A page lives here when it is injection-clean of server types (no `UserManager`/`SignInManager`/`HttpContext`); pages with real backend coupling stay in Himinbjörg's `Identity.Web.Server` until ported clean. The migration proceeds page by page under that rule. Pages keep the ASP.NET Identity scaffold's `/Account/*` routes deliberately — route renaming is a separate, deferred curation pass.

## Architecture Facts (decided — do not re-litigate)

- **Wire purity (ruled 2026-07-27):** the wire records are pure `[DataContract]` shapes — no mediator markers, no `[Authorize]`, nothing WASM doesn't need. Mediator identity and authorization policy live server-side on Himinbjörg's command wrappers (Asgard's `CommandRequest<TRequest,TResponse>`), which only *name* policies; policy registration happens at the consuming host's composition root (Yggdrasil), never here, never Himinbjörg.
- **`LogoutRequest` does not exist** — `IAuthenticationService.Logout` is a `CancellationToken`-only operation, spike-verified end to end through protobuf-net.Grpc. Do not reintroduce a request DTO for it.
- **No issuance result record lives in this realm (2026-08-08, PR #46).** `LoginResult`/`RegisterResult`/`LogoutResult` are deleted, not renamed: Login, Register, and Logout return Asgard's `Outcome<NavigationResult>` (one server-resolved `NextUrl`, navigated unconditionally — return URL, 2FA challenge, lockout; only the server knows the map), EmailExists returns `Outcome<BoolResponse>`. The 2026-08-06 `Succeeded`-flag ruling survives the deletion: a rejected login is `Failed(Problem)`, never a success record carrying a false flag — no politely-glanceable booleans. Do not reintroduce a Heimdall-local issuance result record. (The disclosure responses — `PersonalDataResponse`/`MaskedPersonalDataResponse` — are domain payloads, not next hops; they live here deliberately.)
- **Wire-stamped request scalars (2026-08-08):** the serialized email member on every request that carries an email (`LoginRequest`, `RegisterRequest`, `EmailExistsRequest`, `ForgotPasswordRequest`, `ResetPasswordRequest`, `ResendEmailConfirmationRequest`, `ConfirmEmailChangeRequest`, and `ChangeEmailRequest`'s `NewEmail`) is the stamp — `Result<EmailAddress>` — and the form's raw buffer (`EmailInput`) is never serialized; its setter re-stamps on every assignment, so no code path sets text without refreshing the verdict. The buffer name is a contract, not a style: stamp name + `Input` (`OutcomeFormComponentBase.BufferSuffix`) — the field-change echo maps buffer edits onto stamp rules by that convention. Forms MUST bind `<EditForm EditContext="EditContextFor(_request)">` — `Model=` binding bypasses the blur mechanic, and `SubmitAsync` throws on it by design. Every email input names the stamp in FluentUI's `ValidationFieldFor` (`(Expression<Func<Result<EmailAddress>>>)(() => _request.Email)`) while `@bind-Value` stays on the buffer — the input otherwise shows only buffer-keyed messages and every `Email`-keyed rule or server error renders nowhere. Never rename the key with `OverridePropertyName` instead: it would strand the server rerun's and the handlers' `Email` keys.
- **Validators are declared once and run twice.** Every `*RequestValidator` in `AuthN.Components` — `LoginRequestValidator`, `RegisterRequestValidator`, `GetMaskedPersonalDataRequestValidator`, the account-lifecycle seven (`TwoFactorSignIn`, `RecoveryCodeSignIn`, `ForgotPassword`, `ResetPassword`, `ConfirmEmail`, `ConfirmEmailChange`, `ResendEmailConfirmation`), and the account six (`SetPhoneNumber`, `ChangePassword`, `SetPassword`, `ChangeEmail`, `RemoveExternalLogin`, `DeletePersonalData`) — is the single source of validation truth: Blazilla runs them client-side against the wire type directly; Himinbjörg's generated `CommandRequestValidator<TCommand,TRequest,TResponse>` adapter runs the identical classes again server-side. Never duplicate a rule on the server side. Rules register ON the stamp (`RuleFor(x => x.Email)`), with `WithName(nameof(…EmailInput))` for message display only; buffer edits reach the stamp's rules through `OutcomeFormComponentBase.EditContextFor`'s field-change echo — `PropertyName`, and therefore server error keys, stay `Email`, wire-stable. No rule-set gating, ever (ruled 2026-08-06): Blazilla's field-change pass uses a bare `MemberNameValidatorSelector`, so a submit-only rule set is structurally unbuildable — the async email-existence lookup chains under `Cascade(Stop)` behind the shape gate instead. `RegisterRequestValidator` is DI-constructed (`IAuthenticationService` + `ILogger`) and deliberately not a primary constructor — the `RuleFor` chain needs a constructor body.
- **Components inject `I{Contract}Service` directly and consume `Task<Outcome<T>>`** by pattern-matching — there is no gateway, no wrapper type, and no `IAuthenticationGateway` (deleted with Asgard's gateway generator). The transport-dumb seam is DI substitution per host: Himinbjörg registers its real implementation for Blazor Server; Yggdrasil registers Midgard's generated gRPC client wiring for WASM; Bragi's story host registers a fake.
- **The disclosure tier is shaped by unrepresentability:** `GetMyPersonalDataRequest` is deliberately empty — no subject-id field exists, so asking about someone else cannot be expressed. Self-disclosure is full and unmasked; second-party disclosure is masked. The wire-exposed shred trigger is a recorded deliberate deferral (PII spec §7).
- **`RequestContractTests` is a purity lock, not a formality** — it asserts wire records carry no `[Authorize]`, that `AuthN.Services` never references the mediator-law assembly at all (`Assembly.GetReferencedAssemblies()` — the marker family is unnameable from here by construction), that every service method ends with a trailing `CancellationToken`, and that every operation on all three contracts carries `[OperationContract]` — a code-first gRPC method without it is a silently dead endpoint. Extend it when adding wire surface; never weaken it.
- **`ServerValidation/` is the bridge from `Failed(Problem)` to form UX** — `ServerErrorCoordinator` and `EditContextServerErrorsExtensions` project server-side model errors into the `EditContext` so `ModelValidationSummary` renders them with the same machinery as client-side validation; `OutcomeFormComponentBase` is the shared base for outcome-consuming forms (it also owns `EditContextFor`, the stamped-request field-change echo). Both live in Asgard's `Abstractions.Components` since the 2026-08-09 hoist, not in this realm.
- **Forms write `<FormValidator/>` and `OnSubmit`, never `<FluentValidator/>` or `OnValidSubmit`, and bind the submit button's `Disabled="!CanSubmit"`** (2026-08-10; the binding 2026-10-27 — forms submit only when interactive, so a statically rendered form offers no submit; `FormStaticRenderLockTests` locks all twelve). Asgard's `FormValidator` fixes Blazilla's `AsyncMode` on and does not expose it — a page author never decides whether their validator has async rules, and cannot get it wrong for one they did not write. `SubmitAsync` owns the gate and throws when no `FormValidator` is attached, because a validator-less form validates to `true` with zero messages and is otherwise indistinguishable from a valid one. `OnValidSubmit` would run EditForm's own synchronous pass ahead of that gate and skip async rules entirely. Neither this realm nor Mímir references Blazilla any more — it arrives transitively through `Abstractions.Components`.
- **Scaffold class names stay; Bootstrap doesn't.** Headless components keep the Identity scaffold's markup classes (`alert`, `alert-danger`, …); scoped `.razor.css` (see `Shared/StatusMessage.razor.css`) maps them onto the design-token custom properties (`--error`, `--success`). No Bootstrap reference anywhere — don't add one to make scaffold markup "work."
- **`Manage/_Imports.razor` stamps every page with `@layout ManageLayout` and `[Authorize(Policy = AuthNPolicies.Account)]`; `ManagePolicyLockTests` enforces it; `ManageLayout` renders `?status=` through `ManageStatus` — the server is the only author of URLs.**
- **The session-transition seam is realm law (2026-08-11):** `ISessionTransition` / internal `ForceLoadSessionTransition` / `AddNorseSessionTransition()` live in `AuthN.Components` — only the gate performs a forced document load for a sign-in change (NORSE074 enforces). Markup `ForceLoad` is outside NORSE074's reach and is reserved for links to server HTTP endpoints rather than routed pages (`Account/Manage/LinkExternalLogin`): FluentUI routes a same-origin `fluent-link` or `fluent-anchor-button` click through `Blazor.navigateTo` and ignores `target`, and `ForceLoad="true"` relies on FluentUI 5.0.1's `force-load` attribute as the override. Login begins the transition on success, and so do the two-factor and recovery-code forms; Register, ForgotPassword, and ResetPassword soft-`NavigateTo` the server's `NextUrl` (their handlers sign nobody in); Logout is click-to-confirm on Asgard's `OutcomeComponentBase` — a bare GET renders a button and performs nothing. On the Manage tree, SetPhoneNumber (`ProfileForm`), ChangePassword, SetPassword, RemoveExternalLogin, and DeletePersonalData also begin a transition on success (each refreshes or ends the sign-in); ChangeEmail and its resend-verification button answer in place — no navigation at all. Spec: `../Glitnir/docs/Asgard/specs/2026-08-11-session-transition-seam-design.md`.

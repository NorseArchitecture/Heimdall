## 1. What This Repository Is

Heimdall is **the gate** — `Norse.AuthN`: the authn story built on Himinbjörg, presenting login, register, forgot-password, 2FA setup, recovery, and reset uniformly across Blazor Server, WASM, and MAUI, plus the backing gRPC service. Code-wise this repo still depends on nothing above Asgard — `AuthN.Services` and `AuthN.Components` NorseRef only Asgard's `Abstractions.Contracts`/`Abstractions.Components` — but since Himinbjörg's `feature/identity-web-server` merge (`v0.0.5`) the dependency between the two realms is no longer one-directional: Himinbjörg's `Identity.Web.Server` NorseRefs this repo's `AuthN.Services` (to implement the gRPC contract) and `AuthN.Components.FluentUI` (to host the pages still migrating over), confirmed in Himinbjörg's own `csproj` and `CLAUDE.md`. Heimdall is not, therefore, unambiguously "topmost" in the submodule dependency chain anymore — it has a real consumer riding on it from a realm it also builds on.

`AuthN.Components`, `AuthN.Components.FluentUI`, and `AuthN.Services` are live — the Himinbjörg→Heimdall component migration moved the injection-clean subset (Login, Register, Logout, and their validators/requests) over mechanically; components with real backend injections (`UserManager`/`SignInManager`/`HttpContext`) still live on Himinbjörg's side, in `Identity.Web.Server`'s `Components/Pages/**` tree — that branch (`feature/identity-web-server`) merged to Himinbjörg's `master` and shipped as `v0.0.5`, and the gRPC wireup it was pending on is done (Himinbjörg's `AuthenticationService` implements this repo's `IAuthenticationService` for real, `LoginHandler`/`RegisterHandler` driving `SignInManager`/`UserManager` directly); what remains is only the page-by-page migration of that tree over here, still in progress, not a branch-merge blocker. `AuthN.Services` was hoisted out of `AuthN.Components` (2026-07-24) to isolate `IAuthenticationService` (the gRPC contract) and its wire records (`LoginRequest`, `RegisterRequest`, `LoginResult`, `RegisterResult`, `LogoutResult`) from Razor/FluentValidation/Blazilla — a consumer who wants only the gRPC declarations, wrapped in their own components and wired to whatever backend they choose, references this thin assembly and nothing else. The hand-written `IAuthenticationGateway`/`AuthenticationResult` are retired (both interface and wrapper gone as of Asgard commit 5f06a88 which deleted `[GenerateGateway]`, `GatewayGenerator`, and all emission modes entirely). Components inject `IAuthenticationService` directly — the transport-dumb seam is DI substitution per host: Himinbjörg's `Identity.Web.Server` registers this repo's `AuthenticationService` implementation for Blazor Server; Yggdrasil (via Midgard) registers the generated gRPC client wiring for WASM. Components consume `Task<Outcome<T>>` from `IAuthenticationService` and pattern-match the result; there is no more `AuthenticationResult` wrapper anywhere. Himinbjörg's `Identity.Web.Server` and Yggdrasil's `Hosting.Web.Client`/`Hosting.Web.Server`/`Hosting.Stories.Client` already carry the correct split `using` statements (`Norse.AuthN.Components`/`.FluentUI` for the validators and markup, `Norse.AuthN.Services` for the contract and wire types) — confirmed against both repos' current source, this is no longer an open follow-up. Pages still carry the ASP.NET Identity scaffold's `/Account/*` routes deliberately — route renaming is a separate, deferred curation pass, not bundled into relocation. Before writing anything beyond this slice: brainstorm → spec → plan, recorded in `../Glitnir/docs/Heimdall/`, per the org's spec-first discipline. Do not scaffold ahead of a converged spec. Every plan's REQUIRED SUB-SKILL line names `superpowers:subagent-driven-development` as the default (not a recommendation among equals — `executing-plans` is the narrow fallback for separate-session review checkpoints) paired with `superpowers:test-driven-development` — implementation here is subagent-orchestrated and test-driven, never one without the other (`../Glitnir/CLAUDE.md` §2.8).

**Wire purity ruled 2026-07-27 (mediator-pipeline-retires-gateway amendment):** `LoginRequest`/`RegisterRequest` carry no mediator marker (`ICommandRequest<T>` is gone from both) and no `[Authorize]` — pure `[DataContract]` wire shapes, nothing else, keeping the WASM footprint lean. `LogoutRequest` is deleted outright; `IAuthenticationService.Logout` is a `CancellationToken`-only operation, spike-verified against a real `TestServer`/HTTP-2 round trip through `CreateGrpcService<T>` before this landed — protobuf-net.Grpc needs no request DTO at all for a unary call, and neither Midgard's `ContractDiscovery` nor its two registration emitters ever inspect method parameters, only return types, so the CT-only shape required zero Midgard changes. `Register` now returns `Task<Outcome<RegisterResult>>` (new bare-`Succeeded` wire record) in place of `Task<Outcome<Unit>>`. Mediator identity and `[Authorize(Policy = AuthNPolicies.Public)]` moved server-side entirely, onto Himinbjörg's `LoginCommand`/`RegisterCommand`/`LogoutCommand` — one-line wrappers over these exact wire records via Asgard's `CommandRequest<TRequest,TResponse>` (`Abstractions.Web.Server`). `LoginRequestValidator`/`RegisterRequestValidator` here remain the platform's single source of validation truth: unchanged themselves, they're now reused twice — Blazilla runs them client-side against the wire type directly, and Himinbjörg's generated `CommandRequestValidator<TCommand,TRequest,TResponse>` adapter reaches through the command wrapper and runs the identical class again server-side. `RequestContractTests` is now a purity lock guarding this ruling against future drift, not a "requests are marked commands" assertion — `Wire_records_carry_no_Authorize_attribute` plus, since the marker family itself moved into `Norse.Abstractions.Web.Server` (2026-07-27, same-day follow-up amendment: server-only law belongs in the server-only assembly, so nothing WASM-shipped could decorate a wire type with it again), the strengthened `AuthN_Services_does_not_reference_the_mediator_law_assembly` — asserting `Norse.AuthN.Services`' own `Assembly.GetReferencedAssemblies()` never names `Norse.Abstractions.Web.Server` at all, since the prior "doesn't implement `IRequest<>`" form became inexpressible from this assembly the moment the marker moved (it can no longer even name the type).

**Disclosure contract added 2026-08-04 (Task 19a, `feature/pii-disclosure-contract`):** `AuthN.Services` now carries a second wire tier beside the issuance contract — `IIdentityService` (`grpc.identity.v1.IdentityService`), four wire records (`GetMyPersonalDataRequest`, deliberately empty — no subject-id field exists, so asking about someone else is unrepresentable, spec §6.1; `GetMaskedPersonalDataRequest`; `PersonalDataResponse`; `MaskedPersonalDataResponse`), and `IdentityPolicies` (constants only — `Self`, `MaskedDisclosure`, `SystemRole` — the `RequireRole`/policy registration stays server-side, Himinbjörg's job in Task 19b). `GetMaskedPersonalDataRequestValidator` lands beside `LoginRequestValidator`/`RegisterRequestValidator` in `AuthN.Components`, same dual-run shape (Blazilla client-side, Himinbjörg's generated `CommandRequestValidator` adapter server-side); `GetMyPersonalDataRequest` gets no validator — nothing to validate is the point. `RequestContractTests` (the purity lock) now covers all four new wire shapes in `Wire_records_carry_no_Authorize_attribute`, and `Every_service_method_ends_with_a_trailing_cancellation_token` walks `IIdentityService` alongside `IAuthenticationService`. `PersonalData.razor` ports over from Himinbjörg's `Identity.Web.Server` in the same slice — injection-clean of server types, not injection-count-of-one: three injections (`IIdentityService`, `NavigationManager`, `IJSRuntime` for the client-side download), zero server coupling — no `UserManager`, no `HttpContext` cascade, no `IdentityRedirectManager`, no form-POST. The Download button is now a `GetMyPersonalDataAsync` gRPC call, materializing the JSON file client-side via a small JS-interop helper (`AuthN.Components.FluentUI/wwwroot/downloadFile.js`) — `JSON.stringify` runs there deliberately, since NORSE070 bans `System.Text.Json` calls from this repo's own C#, and the marshaled record crosses the JS interop boundary as a plain object, not a string this code serialized itself. The imported JS module reference is cached on the component and disposed via `IAsyncDisposable` (not re-imported per click), which also means the base `AsyncComponentBase.Dispose()` is called explicitly from `DisposeAsync` — the framework runs only one disposal overload when both are implemented, never both. The delete link is a plain relative `Href="Account/Manage/DeletePersonalData"`, identical to Himinbjörg's original and every other scaffold route — `NavigationManager.ToAbsoluteUri` was tried and reverted; it resolves against the current app's own base URI, which is no different in effect from a relative href, so it solved nothing about cross-host link resolution. That question (if it's a real one at all) is pre-existing and belongs to the page-by-page migration sweep, not this task. `DeletePersonalData.razor` stays in Himinbjörg; its `UserManager.DeleteAsync` semantics are superseded by the shred ceremony (Task 18), and the wire-exposed shred trigger is a recorded deliberate deferral (spec §7, Syn DSAR trigger). This task carries its own ship gate: Himinbjörg consumes this repo via a floating `PackageReference` (`Norse.AuthN.Services`, `Version="*"`), so Task 19b cannot compile until the amended package is published.
